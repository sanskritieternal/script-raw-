# Production bible detail standard

## What a completed document must provide

An applicable production document is an operational specification, not a paragraph saying what it would contain. Write the actual episode decisions, rationale, examples, scene/entity references, exceptions and acceptance checks. A person preparing references, prompts, narration or an edit should be able to use it without inventing the missing creative decisions.

Do not condense a requested full bible to make it fit one response. Write complete files directly. If output must be staged, finish coherent files or sections, record precisely what remains and continue. A response summary can be short; the saved production documents must retain their detail. Do not use repeated boilerplate or unrelated history to inflate length.

Scope detail to the real episode: two characters need two complete relevant profiles, not an invented eight-character cast. A single room needs a usable layout, lighting and continuity specification, not ten invented locations. Financial and quantitative-data documents may remain brief when justified Not applicable. Neither a word count nor passing structural validation establishes editorial depth.

## Per-file content requirements

| Document or group | Required practical detail |
|---|---|
| Consistency rules | Exact configuration values; authoritative document ownership; identity/visual/audio/timing locks; protected fields; allowed exceptions; revision propagation; worked continuity failure and correction |
| Research sources | Claim-to-passage map; named textual/version scope; translation attribution limits; citation use in narration/metadata; what evidence cannot establish; links to Phase 1 |
| Accuracy checklist | Actual episode assertions and verification status; interpretation/design boundaries; unresolved review; tests for name, chronology, object and quotation errors |
| Main characters | One expanded profile per individual: role, motivation supported by the work, narrative arc, observable behaviour, design, expressions, gestures, voice approach, costume/props, scene use, references and limits |
| Supporting characters | One entry per relevant entity; name/aliases, story function, relationships, scene mentions, depiction/voice decision and evidence. Explicitly distinguish mentioned entities from depicted cast |
| Appearance lock | Identity traits, proposed/approved status, model-sheet views, expression/scale sheets, scene-active variants, permitted variation, forbidden drift, reusable prompt wording and reference review criteria |
| Locations | Layout and readable spatial relationships, set zones, landmarks, material/palette/light choices, framing constraints, scene progression, allowed variants, evidence versus design and reference requirements |
| Props/costumes | Individual object/outfit specifications, material/scale choices, owner/location, scene-state transitions, transfer/contact rules, attachment references and checks for duplicates, impossible resets or invented inscriptions |
| Relationships/timeline | Sourced versus interpreted relationships, chronological event map, screenplay order, scene ranges, ownership/age/costume state, uncertainty and explicit causality checks |
| Visual style | Palette/material/rendering language, light/contrast, composition, scale, typography/overlays, examples of desired and rejected treatment, design-source links and acceptance criteria |
| Voiceover/dialogue | Actual full script; narrator/cast distinction, language/pronunciation decisions, per-segment delivery, measured-read plan, silence/breath budget, revision process and recording rights status |
| Story beats/chapters | Each chapter's audience question, narrative purpose, new information, emotional direction, action, scene/time range, source claims and transition. A list of titles alone is insufficient |
| Camera/animation | Several fully described shot recipes with intent, subject, framing, motion, entry/exit state, screen direction, representative scene use and failure checks; relevant motion/contact rules |
| Music/sound | Cue regions, intended motifs/ambience, narrator priority, intentional silence, transitions, source/rights requirements, edit synchronization and actual mix review plan |
| Scene template | One worked episode scene plus field explanations, identity/variant/source references, timing, prompt/overlay separation and instructions for downstream revisions |
| Assets | Distinguish designs, references, clip groups and actual takes; IDs, scene links, intended/actual paths, versions, generation/creator information, provenance, rights, status and review evidence |
| Generator profile | Actual selected provider/model when known, verified input/clip capabilities and sources, reference attachment plan, parent/child scene assembly, final timing, execution logging and pending decisions |
| Metadata/strategy | Usable title/description/chapters, source credits, thumbnail brief, pinned comment, truthful positioning, accessibility/distribution decisions and publication fields explicitly pending until known |
| Legal/ethical/bias | Episode-specific depiction, quotation, rights, uncertainty and representation risks; concrete examples of acceptable and rejected framing; mitigation and evidence boundaries. Do not invent legal conclusions |
| Monetization/originality | Project-appropriate revenue assumptions without invented forecasts; audience trust and provenance constraints; bounded comparison and original value; unperformed checks explicitly identified |
| Glossary | Terms used in the episode, accessible definitions, first-use context, spelling/pronunciation-review needs, source or creative status and delivery location |
| Delivery/revision/status | Concrete inventory and acceptance checklist; text versus generated-media boundaries; actual changes and affected records; current validation evidence and genuine remaining work |
| Planner/index | Exact CONFIG timing, chapter/beat/batch mapping and purpose, actual scene links, reconciliation status; generated index remains derived rather than a competing screenplay |

## Review before marking complete

For every applicable document, ask: does it contain the decisions, or merely instructions to make those decisions? Are profile/shot/prop entries individually usable? Do examples agree with the actual scenes and source limits? Are links, IDs and state transitions consistent? Does a generator operator know what reference assets are needed and which do not yet exist?

Do not claim a visual lock is approved because its text specification is complete. Separate an artistic choice from sourced description and a planned asset from a real file. Record pending external execution honestly; it cannot excuse missing editorial content that can be written now.

The Python validators check structure, field presence, mappings, timing, links and freshness. They do not evaluate whether a short paragraph gives enough creative detail. Use this editorial review in addition to those checks, and describe its limitations honestly.

Keep navigation summaries and justified inapplicability concise. Distinguish missing editorial content from genuinely pending model/media/reviewer work. Save complete files in coherent batches rather than truncating to fit a chat response.
